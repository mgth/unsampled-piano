# Rust real-time audio ecosystem and computational feasibility of a polyphonic physics-based piano (state as of Oct 2026)

Research scope: (a) Rust plugin/app frameworks and I/O, (b) DSP and performance-engineering crates, (c) numerical and latency budgets for physical modelling. Research date: 2026-10-21. About 25 tool calls were used. Items marked "(prior knowledge, not re-verified)" come from the researcher's background knowledge and were not confirmed by a source fetched in this session. Treat them as leads, not facts.

## Q1. Plugin/app frameworks, audio/MIDI I/O, GUI, licensing: which stack is viable for Linux-first development, with Windows/macOS later?

### Takeaway
The original **nih-plug** (robbert-vdh) is officially in **maintenance mode**. The community successor is **nice-plug** (BillyDM, Codeberg, v0.2.3, mid-2026), which keeps the same architecture: CLAP + VST3 + standalone, with egui/iced/vizia adapters. **Steinberg relicensed the VST3 SDK under MIT (VST 3.8, Oct 2025)**, so the old "VST3 forces GPLv3" problem now comes only from the *Rust bindings* nih-plug/nice-plug still use (`vst3-sys`, GPLv3). Migrating to permissive bindings is an open, unresolved issue. **clack** (MIT/Apache-2.0) is a feature-complete, low-level CLAP option. **cpal 0.18 (Jun 2026)** gained native **PipeWire and PulseAudio** backends next to ALSA/JACK. For Linux-first development, nice-plug (CLAP + standalone) plus cpal or JACK is the most viable stack today. The licence question decides whether to ship VST3 as GPLv3 or wait for/replace the bindings.

### Cited Findings
**nih-plug / nice-plug**
- nih-plug's README says the framework "is currently in maintenance mode" and points users to a community fork on Codeberg (codeberg.org/BillyDM/nih-plug). Repo stats: about 3.0k stars, 93 open issues, 30 open PRs. — [robbert-vdh/nih-plug](https://github.com/robbert-vdh/nih-plug)
- nih-plug licensing: the framework, libraries and examples are **ISC**. The VST3 bindings used by `nih_export_vst3!()` "are licensed under the GPLv3 license," so VST3 builds must comply with GPLv3 unless the bindings are replaced. — [robbert-vdh/nih-plug](https://github.com/robbert-vdh/nih-plug)
- nih-plug supports VST3 and CLAP through export macros. Standalone binaries come from `nih_export_standalone()`, with "full JACK audio, MIDI, and transport support". GUI: official adapters for **egui, iced, VIZIA**, plus examples for OpenGL, wgpu and softbuffer. "Tested on Linux and Windows, with limited testing on macOS." — [robbert-vdh/nih-plug](https://github.com/robbert-vdh/nih-plug)
- An open upstream issue #274, "VST3: adopt a permissively-licensed binding now that the SDK is MIT", was opened around June 2026 and is still open. — [nih-plug issues](https://github.com/robbert-vdh/nih-plug/issues) (search snippet; the date was not independently confirmed)
- **nice-plug** "started out as a fork of the awesome NIH-plug framework … has since become its own separate community-led project, and is now the recommended toolkit for Rust audio plugin developers". It exports VST3 and CLAP via `nice_export_<api>` macros and includes a bundler and standalone export. Licensing: ISC framework, **GPLv3 VST3 bindings**, MIT/Apache-2.0 baseview adapters. Published as nice-plug 0.2.3, with commits in mid-2026. — [docs.rs nice-plug 0.2.3 README](https://docs.rs/crate/nice-plug/0.2.3/source/README.md); [Codeberg BillyDM](https://codeberg.org/BillyDM/nih-plug)

**clack (CLAP)**

The README calls it "feature-complete" but "under active development and constant refinement" (breaking changes possible), with incomplete docs. **Real-time thread priority**
- `audio_thread_priority` (Mozilla, MPL-2.0, vendored in Firefox at v0.34.0): on Linux it uses **rtkit over D-Bus** by default. The API is `promote_current_thread_to_real_time(buffer_frames, sample_rate)`. — [mozilla/audio_thread_priority](https://github.com/mozilla/audio_thread_priority); [searchfox rt_linux.rs](https://searchfox.org/firefox-main/source/third_party/rust/audio_thread_priority/src/rt_linux.rs)

### Inferences
- **Recommended stack (Linux-first):** nice-plug for CLAP (and VST3 if GPLv3 is acceptable) plus its standalone (JACK) target, *or* a thin custom layer: **clack** for CLAP plus **cpal 0.18** (PipeWire/JACK/ALSA) and **midir** for a standalone. CLAP is the cleanest licensing path (MIT/ISC throughout). VST3 under nice-plug currently means **GPLv3 for the binary**. That is only a problem for a closed-source product. If the project is open source under GPLv3 anyway, the issue disappears.
- Because the VST3 SDK is now MIT, a permissively licensed Rust VST3 binding is legally possible. Whether one has been adopted by nice-plug as of Oct 2026 was not confirmed (see Gaps).
- **Architecture recommendation:** keep the DSP engine in a framework-agnostic crate (pure `process(&mut self, block)` API with no framework types). Wrap it with nice-plug/clack for plugins and with cpal+midir for standalone and offline rendering. This reduces exposure to further churn in the framework layer (nih-plug → nice-plug already happened once).
- GUI: egui (immediate mode, simplest), vizia (audio-oriented, retained), iced. All are available through nice-plug adapters on top of baseview. A physics piano needs only a modest GUI, so egui is the low-risk choice.

### Gaps
- Exact maintenance/commit dates of `midir`, `wmidi`, `midly`, `jack` crate, `pipewire-rs`, `vst3-sys` vs a newer `vst3` crate (e.g. by coupler/micahrj): **not verified this session**. Prior knowledge (not re-verified): midir is the de-facto cross-platform MIDI input crate (ALSA/JACK/CoreMIDI/WinMM); `wmidi` and `midly` are parser crates (live messages and SMF files respectively); the `vst3` crate from the coupler project is a newer, permissively licensed binding generator. Check crates.io before committing.
- Whether nice-plug has switched or will switch to MIT VST3 bindings: issue open, no resolution found.
- Status of Linux Wayland plugin GUIs in baseview: not researched. VST3's Wayland support is only a "preview".

## Q2. DSP crates, SIMD, CPU dispatch, denormals, real-time safety tooling

### Takeaway
**`std::simd` (portable_simd) is still nightly-only and unstabilised in 2026.** On stable Rust the practical options are **`wide`** (no multiversioning), **`pulp`** / **`macerator`** (built-in runtime multiversioning, AVX2/AVX-512, NEON), **`fearless_simd`** (Linebender, reportedly reached v1.0 in 2026 and called "the most complete all-in-one solution" in a 2026 survey), or `multiversion` + intrinsics. For real-time safety, **`assert_no_alloc`** (allocator guard) and **`rtsan-standalone`** (LLVM RealtimeSanitizer wrapper, Linux/macOS) are both usable today. A rustc PR (Oct 2025) aims to add native RTSan support.

### Cited Findings
- portable_simd tracking issue #86656 remains open, with unresolved questions (mask semantics, supported vector sizes). A 2026 survey by Shnatsel concludes "std::simd is nightly-only and incomplete" and calls fearless_simd "the most complete all-in-one solution". — [rust-lang/rust#86656](https://github.com/rust-lang/rust/issues/86656); [summary of Shnatsel 2026 survey](https://zeli.app/story/49844629) (secondary coverage)
- Shnatsel's 2025 survey: **pulp** is "a great design with built-in multiversioning … quite mature and complete", but on x86 it only targets AVX2 and AVX-512 (no older extensions) and it has no WASM. **macerator** is a pulp fork with "vastly expanded instruction set support" but is obscure and unproven. **fearless_simd** copies pulp's design (made for vello), and in 2025 supported NEON/WASM/SSE4.2 but not newer x86. **std::simd** has no built-in multiversioning (needs `-C target-cpu` or the `multiversion` crate). Summary recommendation: "use std::simd if you don't mind nightly, wide if you don't need multiversioning, and otherwise pulp or macerator." — [Shnatsel, "The state of SIMD in Rust in 2025"](https://shnatsel.medium.com/the-state-of-simd-in-rust-in-2025-32c263e5f53d); [Linebender: Towards fearless SIMD, 7 years later](https://linebender.org/blog/towards-fearless-simd/); [docs.rs fearless_simd](https://docs.rs/fearless_simd)
- **rtsan-standalone** (v0.2.0 on docs.rs): wraps LLVM's standalone RealtimeSanitizer. Functions are marked with `#[nonblocking]`, checks are enabled with `RTSAN_ENABLE=1`, and reports print a stack trace of the intercepted call (e.g. `calloc`). It works on **Linux, macOS, iOS** only and downloads prebuilt libraries (needs curl). — [docs.rs rtsan-standalone](https://docs.rs/rtsan-standalone)
- On Linux, RTSan detects mutex blocking only through the futex syscall path. On macOS the first lock can allocate. — [segmentfault write-up](https://segmentfault.com/p/1210000046583359) (secondary, Chinese)
- rust-lang/rust PR #147935 (Oct 2025) proposes native realtime sanitizer support in rustc. Its author notes RTSan "is usable in rust code with the rtsan-standalone crate today". — [rust-lang/rust#147935](https://github.com/rust-lang/rust/pull/147935)
- **assert_no_alloc**: a custom global allocator that "allows to temporarily disable memory (de)allocations for a thread" and aborts or warns on violation, aimed at audio callbacks. It uses thread-local storage. — [Windfisch/rust-assert-no-alloc](https://github.com/Windfisch/rust-assert-no-alloc); [lib.rs](https://lib.rs/crates/assert_no_alloc)

### Inferences
- **SIMD strategy for a modal/waveguide piano:** the hot loop (thousands of independent 2-pole resonators) is embarrassingly data-parallel. A structure-of-arrays layout with mode count padded to a multiple of 8 or 16 auto-vectorises reasonably well, but the Anukari experience (Q3) shows that relying on auto-vectorisation is fragile. Recommended: write the resonator bank kernel once with `pulp` or `fearless_simd` (runtime dispatch AVX2/AVX-512/NEON), and keep a scalar reference implementation for testing. Avoid nightly `std::simd` unless the project accepts a nightly toolchain.
- **Denormals:** decaying modal resonators and feedback loops produce subnormals as notes die away, a classic source of CPU spikes. Set FTZ/DAZ (MXCSR on x86, FPCR on aarch64) at the start of each audio callback, or add a tiny DC/noise offset. Prior knowledge (not re-verified): the `no_denormals` crate offers a scoped guard. nih-plug-style frameworks already set FTZ in the process call. Verify in nice-plug source.
- **Real-time safety CI:** run offline render tests under `assert_no_alloc` (debug builds) and `rtsan-standalone` (Linux CI) to catch allocations, locks and syscalls in `process()`.
- **Lock-free communication (prior knowledge, not re-verified):** `rtrb` (SPSC ring buffer, from the RustAudio/mgeier lineage) for MIDI and events into the audio thread, `ringbuf` as an alternative, `basedrop` (deferred reclamation via a collector thread) or `arc-swap` for swapping large parameter structures such as fitted modal tables, and `triple_buffer` for "latest value" GUI ↔ DSP state. `crossbeam` channels are not wait-free on the receiving side and should be avoided in the callback.
- **DSP helper crates (prior knowledge, not re-verified):** `fundsp` (graph-notation DSP, useful for prototyping post-effects, not for the core physics), `dasp` (sample/frame primitives; low activity), `biquad`, `realfft`/`rustfft` (FFT partitioned convolution for the soundboard IR), `faer` (fast pure-Rust linear algebra, good for offline modal fitting and eigenproblems) vs `nalgebra`/`ndarray`. pyo3/maturin gives Python bindings for fitting and analysis.

### Gaps
- Current versions and maintenance dates for fundsp, dasp, biquad, rustfft/realfft, faer, rtrb, ringbuf, basedrop, arc-swap, triple_buffer, no_denormals, multiversion: lib.rs returned 403 and these were **not verified this session**. Check crates.io before selecting; `dasp` in particular has historically been slow-moving.
- No source found on whether nice-plug wires in FTZ/DAZ or assert_no_alloc by default.

## Q3. Multithreading inside the audio callback, real-time priority, and lessons from GPU physics synths (Anukari)

### Takeaway
The most informative real-world case study is **Anukari** (3D mass-spring physics synth, 1.0 in mid-2026). It ran physics on the GPU (OpenCL → Metal/CUDA) from 2024 to 2025. In **Nov 2025 it moved to the CPU** with hand-written **AVX2/NEON** SIMD, one thread per voice, and ended up "substantially faster" than the GPU in nearly all cases. GPU audio suffered from barrier-synchronised idle threads, GPU clock heuristics that ignore audio, contention with other GPU apps, and a need for **≥ ~512-sample buffers**. For a piano synth, this strongly argues for a **CPU, SIMD, voice-parallel** design, with worker threads promoted to real-time priority.

### Cited Findings
- Anukari's original goal was about 10,000 point masses (~50,000 springs) in real time, which napkin math said a CPU could not reach. Problems on GPU: one thread per object with threadgroup barriers per step leaves light objects (e.g. "Anchor") idle while heavy ones (e.g. "Mic", ~10x work) run; threadgroups are capped at ~1,024 threads (16 voices → 16,384 objects in groups of 1,024); float3 force accumulation via atomics is "not really possible"; and other GPU software (a VJ visualiser) starved the physics. The naive CPU port was only ~5x slower than the GPU, not the 100x expected. — [Anukari devlog: "Anukari on the CPU (part 1: GPU issues)", Nov 2025](https://anukari.com/blog/devlog/anukari-on-the-cpu-part-1-gpu-issues)
- CPU optimisation: hand-written **AVX2** (8 floats) on x86 and **NEON** (4 floats) on arm64, with separate implementations per ISA. AVX2 is the minimum supported on Windows/Linux/Intel Macs; AVX-512 is not used. The author switched from SoA to **AoS {x,y,z,w}** for randomly accessed float3 data (SoA wastes ~180 B of bandwidth per random lookup vs ~32 B for AoS). **Fusing gather → compute → scatter in a single pass gave a 3–4x speedup** on the spring loop. Other techniques: pad arrays to SIMD width instead of remainder loops, sort springs by memory address, keep state in registers. Prefetching gave no benefit. Auto-vectorisation was "very conservative" (MSVC lists 35+ reasons for skipped loops), and intrinsics were simpler and more predictable. "Memory layout and cache behavior mattered more than raw arithmetic." Final result: "substantially faster" than the GPU in nearly all cases. — [Anukari devlog part 2: CPU optimization, Nov 2025](https://anukari.com/blog/devlog/anukari-on-the-cpu-part-2-cpu-optimization)
- On the CPU, each voice runs on its own thread and steps through all objects sequentially, so no barrier is needed and no thread sits idle. — [Anukari devlog part 1](https://anukari.com/blog/devlog/anukari-on-the-cpu-part-1-gpu-issues)
- Further GPU-era lessons from the devlog index: macOS does not raise GPU clocks for latency-sensitive audio, and burning one warp on dummy work cut latency by ~40% ("Waste makes haste", Nov 2024). Metal kernel launch overhead was reduced below 50 µs (May 2025). OpenCL's 256-thread cap doubled latency on large presets (fixed in CUDA with 1024-thread blocks). The physics detects "explosions" from oversized time steps by tracking peak velocity and resets the voice. When GarageBand stopped calling the audio callback, physics moved to a background thread. — [Anukari devlog index](https://anukari.com/blog/devlog)
- The developer stated that because Anukari uses the GPU for audio it "really needs a buffer size of at least ~512" to perform comfortably (beta period). — [KVR forum thread](https://www.kvraudio.com/forum/viewtopic.php?p=9078822)
- Anukari 1.0 was reported in June 2026 (single secondary source). The devlog shows "The path to 1.0" (Jun 2026) and Linux support news (Aug 2026). — [Dubspot](https://blog.dubspot.com/anukari-3d-physics-synthesizer-2026); [Anukari devlog index](https://anukari.com/blog/devlog)
- Linux RT priority for worker threads: `audio_thread_priority` can promote *any* thread (not just the host's callback) through rtkit or SCHED_FIFO. cpal 0.18.2 had to fix "rtkit burst-limit errors" in its PipeWire backend, which shows rtkit limits (RLIMIT_RTTIME and burst limits) are a real pitfall. — [mozilla/audio_thread_priority](https://github.com/mozilla/audio_thread_priority); [cpal releases](https://github.com/RustAudio/cpal/releases)

### Inferences
- **Threading design:** with a 64–256-sample block, a voice-parallel fork/join inside `process()` is feasible. Use N pre-spawned worker threads promoted to RT priority, each spinning or waiting on a futex or semaphore, with voices partitioned per block and a sum-reduction at the end. Pitfalls: (1) workers must be RT-promoted or they get preempted and cause xruns; (2) spinning burns CPU and fights with the host's own thread pool in a plugin context. Many DAWs already parallelise across tracks, so inside a plugin, single-threaded SIMD is often the safer default, and internal threading should be optional. In the standalone app, internal threading is fully under your control. (3) Synchronisation cost per block (~µs) must stay small relative to the block period (1.33 ms at 64 samples / 48 kHz).
- Prior knowledge (not re-verified): Vital and Surge render voices single-threaded with SIMD (Surge processes voices in SSE "quad" groups). Commercial physical-model pianos (Commercial) are mostly single-thread per instance with optional multi-core. This could not be confirmed with sources this session.
- **GPU for a piano: not recommended** for the core real-time path. The Anukari evidence (≥512-sample buffers, ~10.7 ms at 48 kHz, plus vendor-specific clock and launch issues) conflicts with the low-latency (≤128-sample) feel a piano needs. A piano's DSP (a few thousand modes per voice) fits comfortably on CPU SIMD (see Q4). GPU could still be useful *offline* for parameter fitting or high-resolution FDTD reference renders.
- Physics-explosion detection (peak-velocity or energy watchdog with voice reset) is a useful safety net even with provably passive schemes, because parameter edits or modulation can break assumptions.

### Gaps
- No primary source found on GPU Audio Inc.'s SDK status or latency figures in 2025–2026.
- No published Rust-specific benchmark of a worker-pool voice renderer found.
- Bilbao/Webb/Perry NESS GPU work: not retrieved this session (prior knowledge, not re-verified: NESS used CUDA for *offline* large-scale FDTD such as 3D rooms, brass and nonlinear plates, not real-time).

## Q4. Computational budgets: waveguide vs modal vs FDTD, published real-time numbers, cost per core at 48 kHz

### Takeaway
Published data points: (1) **van Walstijn, Bhanuprakash & Chatziioannou (DAFx 2023)**: an explicit, energy-quadratised **modal hammer-string** scheme runs at **real-time factor < 0.75 in *Matlab* on an i7-6700 for up to 1000 modes with block size ≥ 32**. A0 (lowest piano key) needs about **300 modes** to cover the audio band. (2) **Russo, Ducceschi & Bilbao (DAFx 2022)**: a modal stiff string with a non-iterative bow nonlinearity runs "in real-time at high sample rates even in Matlab". (3) **Bank, Zambon & Fontana (IEEE TASLP 2010)**: a full modal piano (transverse + longitudinal modes, FFT or parallel-filter soundboard) "runs on current computer hardware with full polyphony". Back-of-envelope arithmetic (see Inferences) suggests one modern AVX2 core can update on the order of **10⁴–10⁵ damped modes at 48 kHz**. That supports a full-polyphony modal piano on 1–2 cores, while FDTD stiff strings for the whole keyboard are feasible but much tighter.

### Cited Findings
- DAFx23, "Tunable collisions: hammer-string simulation with time-variant parameters" (van Walstijn, Bhanuprakash, Chatziioannou): a modally expanded string plus an **explicit scheme built by quadratising the contact energy** (IEQ/SAV-style). The numerical energy balance is derived and the contact force is "strictly non-adhesive". Out-of-range modes (above 0.9·Nyquist) are suppressed with a weight function. Hammer-string contact runs at 44.1 kHz with **OF = 1**, compared against a reference "approximated with 24 times oversampling". Under time-varying tension, OF = 2 is taken as "nominally correct", and block-wise parameter updates with Nb = 128 give artefacts "more than 60 dB below the level of the partial tones". **Computational efficiency:** RTF averaged over 50 runs of randomised hammering (C2 parameters), "performed in Matlab on an Intel i7-6700 CPU … the RTF remains below 0.75 for block sizes of 32 and above with up to 1000 string modes. For reference, the number of modes needed to cover the audio range for an A0 … is about 300." The authors note big gains are expected from optimised C++ with AVX because of the uncoupled modal update. — [DAFx23 paper 18](https://www.dafx.de/paper-archive/2023/DAFx23_paper_18.pdf)
- DAFx 2022, "Efficient simulation of the bowed string in modal form" (Russo, Ducceschi, Bilbao): non-iterative (energy-stable) schemes give results comparable to fully implicit Newton-Raphson methods while avoiding iteration. Forward Euler is unstable at high bow force. With modal semi-discretisation "a fast algorithm is available, yielding compute times below real-time for typical musical strings". For the stiff string "the algorithm runs in real-time at high sample rates even in Matlab" (fs = OS·44100). Stiffness *reduces* the number of in-band modes and so lowers cost. Modal form lets you set a per-mode decay "without any additional computational effort". — [DAFx 2022 (mdphys.org)](https://www.mdphys.org/PDF/dafx_2022.pdf)
- Bank, Zambon, Fontana, "A Modal-Based Real-Time Piano Synthesizer", IEEE TASLP 18(4):809–821, May 2010: transverse and longitudinal string motion via modal synthesis gives a "highly parallel model structure". The soundboard uses FFT-based fast convolution or parallel second-order filters. The paper discusses per-block complexity, stability and aliasing, and states the model "runs on current computer hardware with full polyphony". — [Bank's sound-example page](https://home.mit.bme.hu/~bank/publist/taslp-piano/index.html); [IRIS Univr record/full text](https://iris.univr.it/handle/11562/342223)
- Follow-up: Gabrielli, Zambon, Fontana (EUSIPCO 2015) propose a parallel DSP architecture for the acoustic piano on embedded processors. — [EUSIPCO 2015 PDF](https://new.eurasip.org/Proceedings/Eusipco/Eusipco2015/papers/1570104271.pdf)
- DAFx 2019, "Large-scale real-time modular physical modeling sound synthesis" (Bilbao, Ducceschi et al.): a real-time modular system of strings and bars with nonlinear contact connections, using an "energy-stable non-iterative" discretisation. — [DAFx2019 paper 22](https://dafx.de/paper-archive/2019/DAFx2019_paper_22.pdf)
- DAFx 2023, "Real-time gong synthesis" (Ducceschi, Bilbao et al.): an energy-balanced scheme in which the nonlinearity "can be solved explicitly, allowing for an efficient solution in real time", based on quadratised energy. — [DAFx23 paper 19](https://www.dafx.de/paper-archive/2023/DAFx23_paper_19.pdf)
- 2026 preprint "nlm: Real-Time Non-linear Modal Synthesis in Max" shows a current real-time nonlinear modal implementation (not read in detail). — [arXiv 2603.10240](https://arxiv.org/pdf/2603.10240)

### Inferences (researcher's own arithmetic; check before relying on it)
- **Latency budgets at 48 kHz:** 64 samples = 1.33 ms, 128 = 2.67 ms, 256 = 5.33 ms per callback. Target ≤ 50–70% of the period for worst-case DSP to leave headroom for the host, OS jitter and GUI.
- **Modal resonator cost:** one damped mode as a complex one-pole (or real 2-pole) is ~3–4 multiply-adds plus input injection, about **6–10 flops/mode/sample**. That is ≈ 0.3–0.5 MFLOP/s per mode at 48 kHz. One AVX2 core (8 fp32 lanes × 2 FMA ports × ~3.5–4.5 GHz) peaks around 200+ GFLOP/s. At a realistic 20–30% of peak, that is **~40–60 GFLOP/s, or ~10⁵ modes/core**. At a conservative 10% of peak, that is still ~2–4·10⁴ modes. AVX-512 roughly doubles lane width where available.
- **Piano voice size:** about 300 modes for A0 (DAFx23), fewer in the treble (stiffness and high f0 leave few partials below Nyquist). There are 1–3 strings per key, with optional second polarisation and longitudinal modes (Bank 2010). An average of maybe 200–600 modes per voice gives **50–200 voices per core**, which covers full piano polyphony including sustain-pedal sympathetic resonance. *Caveat:* the hammer nonlinearity (power-law contact, explicit SAV/IEQ update) is active for only ~1–4 ms per strike and adds a projection over all modes (O(M) per sample). That is cheap but must not be forgotten in coupling-heavy designs.
- **Digital waveguide string:** delay line + loss filter + fractional delay + dispersion cascade of K second-order allpasses (K ≈ 4–16 in the bass) ≈ 20–100 flops/sample per string, which is cheaper than modal per string. However, inharmonicity tuning and hammer/bridge coupling are less "physical", and passivity relies on filter design.
- **FDTD stiff string:** grid points N ≈ L/h, bounded by the stability condition. For an ideal string N ≈ fs/(2 f0): A0 at 48 kHz gives ~870 points, C4 ~92 points, before stiffness raises h_min (fewer points) or oversampling raises fs (more points). At ~10 flops/point (5-point stencil), A0 costs ≈ 0.4 GFLOP/s per string. A full 88-key, ~220-string FDTD instrument with 2x oversampling is therefore around 10–40 GFLOP/s. That is feasible on several cores with SIMD, but much less headroom than modal. Modal also allows exact (analytically discretised) per-mode frequency and decay, avoiding FD numerical dispersion and frequency warping.
- **Soundboard/body:** best treated as **one shared post-mix stage** (partitioned FFT convolution of a measured or synthetic IR, or a few hundred parallel second-order sections as in Bank 2010), not per voice. Cost: a few % of a core.
- **Oversampling:** modal-form hammer contact with an explicit energy-quadratised scheme appears acceptable at OF = 1–2 (DAFx23). FD schemes and strongly nonlinear coupled systems (string-bridge-soundboard contact, geometric nonlinearity / phantom partials) more often need 2x or more. With modal synthesis, aliasing from the contact nonlinearity is partly mitigated by simply not having modes above ~0.9·Nyquist.
- **Overall feasibility verdict:** a modal (or hybrid modal + waveguide) piano with energy-stable explicit hammer contact, a shared soundboard convolution and full 88-key sympathetic resonance is **comfortably feasible in real time on 1–2 modern x86/ARM cores at 48 kHz with 64–128-sample buffers**, given SoA/AoS-aware SIMD kernels. Full-keyboard FDTD is feasible but risky. GPU is unnecessary and latency-hostile.

### Gaps

- Exact numbers from DAFx22 Table 2 (run-time ratios vs oversampling) were not extracted cleanly. Only the qualitative statement is cited.

## Q5. Numerical methods for stable real-time models, and testing/tooling

### Takeaway
The 2019–2026 literature has converged on **explicit, non-iterative, provably energy-stable schemes** built on **energy quadratisation (IEQ/SAV)**, often in **modal form**: Ducceschi, Bilbao, Russo, van Walstijn, Bhanuprakash, Chatziioannou. These remove Newton-Raphson iterations (bad for real time and parallelism) while guaranteeing passivity and, for contacts, non-adhesion. A 2026 *Nonlinear Dynamics* paper studies SAV's numerical convergence for nonlinear stiff strings. WDF and port-Hamiltonian approaches remain alternatives, but no new sources on them were retrieved in this session.

### Cited Findings
- The DAFx23 hammer-string paper builds "an explicit scheme … based on quadratising the contact energy … following similar principles as applied in IEQ and SAV methods". It derives a numerical energy balance, shows the contact force is strictly non-adhesive, and supports online, time-variant parameter changes (tension, contact stiffness, power-law exponent) at audio rate. It notes that prior iterative solvers "severely reduce the scope for parallelisation and real-time implementation". In a 29-parameter string-bridge-plate model, iterative solvers forced empirical limits on parameter-change rates to avoid instability. — [DAFx23 paper 18](https://www.dafx.de/paper-archive/2023/DAFx23_paper_18.pdf)
- Russo, Ducceschi, Bilbao (Nonlinear Dynamics, 2026), "Numerical convergence of the scalar auxiliary variable method applied to nonlinear stiff string models": under the stability condition all energy contributions are non-negative and the method is energy-conservative and stable. — [Springer, Nonlinear Dyn. 2026](https://link.springer.com/article/10.1007/s11071-026-12708-0)
- Ducceschi & Bilbao (J. Sound Vib. 2022), "Simulation of the geometrically exact nonlinear string via energy quadratisation". — [JSV 2022 PDF](https://mdphys.org/PDF/jsv_2022.pdf)
- DAFx22: non-iterative energy-stable schemes "outperform classic explicit integrators such as Forward-Euler in terms of stability" and match implicit Newton-Raphson results. — [DAFx 2022](https://www.mdphys.org/PDF/dafx_2022.pdf)
- Earlier foundation: energy-conserving schemes for musical-instrument contact/collision dynamics (Bilbao, Torin, Chatziioannou). — [arXiv 1501.01493](https://arxiv.org/pdf/1501.01493)
- Anukari's testing practice: **FFT-based audio-clip comparison for golden tests** (Jun 2024), fuzz tests, and a "chaos monkey" (Dec 2024). — [Anukari devlog index](https://anukari.com/blog/devlog)

### Inferences
- **Recommended numerical core:** a modal string (exact per-mode discretisation of linear frequency and damping), plus an explicit SAV/IEQ hammer contact (DAFx23 recipe), plus a shared soundboard. Every update is explicit, O(M) per sample and SIMD-friendly. Energy balance can be monitored in debug builds as a regression invariant (the "numerical Hamiltonian" should never increase without input).
- **Coupling** (strings ↔ bridge ↔ soundboard, unison detuning, sympathetic resonance) can be done in modal form via low-rank projections. Keep it explicit and non-iterative to preserve real-time determinism.
- **Testing/tooling plan:** (1) an offline renderer binary (same engine crate, file-in/WAV-out, deterministic) for golden-file and spectral-distance tests against reference recordings, following Anukari's FFT-comparison approach; (2) criterion microbenchmarks per kernel (modes/s, per-voice ns/sample); (3) `perf` / flamegraph on Linux; (4) `assert_no_alloc` + `rtsan-standalone` in CI; (5) pyo3 bindings for Python-side fitting (modal frequencies, decays, inharmonicity B, hammer parameters) with numpy/scipy, sharing the exact Rust kernels; (6) hot-reload of parameter tables via `arc-swap`/`basedrop` from a file watcher.

### Gaps
- No 2024–2026 sources retrieved this session on **wave digital filters** for the piano hammer (Werner, Fettweis lineage) or on **port-Hamiltonian real-time audio** (Falaize & Hélie; Müller & Hélie). Prior knowledge (not re-verified): PHS gives passive-by-construction discretisations via discrete gradients, which often need implicit/iterative solves (with explicit variants via SAV-like reformulations). WDFs handle a single nonlinearity non-iteratively but get awkward with multiple nonlinearities. The report writer should treat these as background only.
- No source quantifying audible aliasing from hammer contact at OF = 1 vs 2 in modal form beyond the DAFx23 comparisons.
